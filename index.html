Project · Flutter · Online and offline

The King's Court

A cooperative trick-taking card game for two to six players. Everyone plays together: each round deals tasks, the court shares them out, and the round is won only if every task is done.

  • Flutter
  • Dart
  • GitHub Actions
  • GitHub Pages
  • Cloudflare Workers
  • Durable Objects
  • D1
  • Python
Play it in the browser Read the code

It started as a companion app for a card game I like and became the project where I test how far a Flutter codebase can be pushed toward real engineering discipline. It runs on the web for quick testing on a phone, has bots to fill empty seats, three skins, a tutorial, a bug-report button, and online rooms. A printed deck and box are generated from the same brand file as the app.

  • The rules engine is plain Dart with no Flutter in it

    Why: the same rules and the same bots have to run on a server for online play. A test reads every import in the project and fails if one points the wrong way between layers, so the boundary cannot erode quietly.

  • Every move is an action that serialises to JSON, and all randomness comes from one seed

    Why: a game replays exactly from its setup and its moves, a bug report carries enough to reproduce the bug, and two devices stay in step. A fake network that delays, reorders, duplicates and drops messages proves it.

  • The bots play fair

    Why: a bot that reads hidden hands is no use for balancing or for fun. Bots infer what is known about the other hands and sample plausible deals, and a test fails if a bot ever acts on a card it cannot see.

  • CI is the build machine

    Why: I often work in sessions with no Flutter SDK. Every branch runs a strict analyzer (any finding fails), the tests, 70 screenshots compared against a baseline, and a benchmark that fails a branch running 30% or more slower than main on both runs.

  • The web build is the JavaScript one, not WebAssembly

    Why: the WebAssembly build ran badly on iOS Safari, and I test on my phone.

  • One Skin object, and a test that fails if a widget names a colour

    Why: reskinning, including possible paid skins, then means writing a skin and never touching a widget.

  • Versioned saves with a migration and a fixture for every version

    Why: players keep their games across releases. A test loads every save format the game has ever written.

  • A small Cloudflare Worker for bug reports and play data

    Why: "Report a bug" in the game opens a GitHub issue with the full game state attached. Rounds people play are stored in D1 so bots can play thousands of rounds when the rules change and I can see what the task mix does to win rates. Sharing play data can be switched off in the menu.

Follow Me Therapy

The website for a paediatric occupational therapy practice, and the design system behind it. The same tokens drive the site, the printable worksheets, a book and a Kotlin Multiplatform app.

Visit the site Read the code

The practice owner works in accessibility, so the bar is WCAG 2.2 AAA, not AA. That shaped most of the engineering: the site is static and framework-free, and the interesting work is in the checks that keep every product consistent.

The app is a Kotlin Multiplatform project still in progress. It is not linked here because it is a health product, but it is the main reason the design tokens generate Kotlin as well as CSS.

  • Design tokens are the single source for every colour, font and size

    Why: a JSON file builds the CSS variables, the component library and the app's Kotlin. A check fails the build on any colour, font size, radius or duration written by hand, so the website, worksheets and app cannot drift apart.

  • Accessibility is a build gate, not an audit

    Why: text must hold 7:1 contrast on its fill in every tone it is used in, targets are 44px, and an automated accessibility run must report no violations before anything is called done.

  • Landing pages are generated from one Python file

    Why: the local-service pages share content and structure. Editing one source avoids hand-edited copies diverging, and CI regenerates them whenever the design changes.

  • Changes go to a preview branch first, linked by commit hash

    Why: the practice owner reviews before anything is live. Preview links use the commit hash because the preview host caches branch URLs. Going live is a fast-forward of main.

  • The link-preview image is rendered by CI from the site's own CSS

    Why: chat apps cache share images by URL, so each render gets a content-hashed filename and every reference is updated, and the image can never fall out of date with the design.

Sage Connection

A website for a community of experienced women who connect, support and empower one another.

  • HTML
  • CSS
  • JavaScript
  • GitHub Pages
Read the code

  • One static page with no build step

    Why: the people who run the community should be able to understand and change it. There is nothing to install and hosting is free.

  • Content is visible without JavaScript

    Why: scroll animations only switch on when a script adds a class to the page, so a failed script never leaves sections hidden.

  • Team photos are compressed, lazy loaded and hidden until decoded

    Why: the first version had images popping in as they arrived, which looked broken on slow connections.

How I work with AI agents

I use AI coding agents every day, and I treat their output the way I would treat a new hire's: welcome, and checked.

  • Each repository has a rules file the agent reads first

    Why: it states the one rule (behaviour must not change unless it is meant to), the layer boundaries, how to run checks and the branch workflow. Never push to main without being told, and small commits of one sentence each.

  • CI proves every change, nobody reads and hopes

    Why: analyzer, tests, screenshot diffs and performance budgets turn "looks right" into a pass or fail. A red commit is fixed before anything else.

  • Decisions are written down as they are made

    Why: a decisions file records every call made without asking and every deliberate behaviour change, with the screenshots that explain it. A later session, or a person, can see why something is the way it is.

  • A human reviews what ships

    Why: at work I added AI to CI/CD, ticket writing and technical documents, and every output was reviewed by a person. The side projects follow the same rule.
